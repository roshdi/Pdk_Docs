PDK Vision

Mission

Prime Development Kit is an enterprise .NET development platform that removes repeatable application infrastructure from day-to-day product development. Teams describe application structure with strongly typed metadata, and PDK generates the consistent infrastructure needed to implement that structure.

PDK enables developers to spend their time on domain behavior and business rules instead of recreating projects, APIs, persistence plumbing, contracts, permissions, mappings, and user-interface metadata.

Primary Audience

PDK is primarily designed for enterprise .NET teams building long-lived business applications. These teams typically need:

  • Consistency across services and contributors
  • Repeatable architectural boundaries
  • Strong typing and compile-time feedback
  • Safe regeneration as applications evolve
  • A clear separation between infrastructure and business behavior

PDK may also support architects and platform engineering teams, but their needs must serve the primary goal of improving enterprise application delivery.

Product Identity

PDK is a development platform, not only a code generator or runtime framework. It combines:

  • Definition libraries for describing platforms, services, entities, and capabilities
  • Discovery and metadata processing
  • Project and source-code generation
  • CLI and build integration
  • Runtime libraries used by generated applications
  • Conventions for backend services and metadata-driven user interfaces

These parts should form one coherent developer workflow.

Generation Lifecycle

pdk new platform creates the platform solution and its Platform project. The Platform project owns the strongly typed platform definition. After that project builds, its MSBuild target invokes pdk generate api <assemblyPath> <projectPath>. The CLI loads the compiled definition by reflection, validates it, and generates or updates the Core and API projects for every registered built-in and business service. The generated service projects are added to both the platform solution and their service solution. Rebuilding the Platform project repeats this process, keeping generated structure synchronized with the definition while preserving developer-owned files.

Goals

PDK should:

  1. Eliminate repetitive infrastructure code through metadata-driven generation.
  2. Enforce consistent architectural conventions across applications and teams.
  3. Keep application structure strongly typed, discoverable, and reviewable in code.
  4. Make generated infrastructure safe to discard and regenerate.
  5. Keep business logic in developer-owned code.
  6. Support equivalent explicit CLI and build-integrated generation workflows.
  7. Preserve compatibility of platform definitions as PDK evolves.

Non-Goals

PDK does not generate business rules or domain behavior. Generated code may provide extension points, base implementations, and infrastructure, but the meaning and behavior of the business domain remain developer-owned.

PDK is intentionally opinionated. Supporting every possible application architecture is less important than providing a coherent and productive model for its chosen architecture.

Success Criteria

PDK is successful when:

  • A business capability can be described with substantially less infrastructure code.
  • Generated services follow the same conventions without manual enforcement.
  • Regeneration does not destroy handwritten behavior.
  • Definitions remain understandable without reading generated output.
  • Developers receive useful failures when definitions are incomplete or invalid.
  • CLI and build generation produce equivalent results from the same definitions.
