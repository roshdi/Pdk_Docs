PDK Architecture Principles

These principles guide implementation and review decisions. A change that conflicts with a principle should include an explicit architecture discussion and, when accepted, an ADR.

1. Definitions Own Structure

Strongly typed C# definitions are the authoritative description of platform, service, entity, and capability structure. Generated output and runtime reflection are derived from those definitions.

Definitions should be concise, composable, discoverable, and validated with actionable diagnostics.

2. Code Owns Behavior

Business rules and domain behavior belong in handwritten code. Definitions may declare capabilities and generated infrastructure may invoke extension points, but generation must not invent business decisions.

3. Generated Code Is Disposable

Developers do not edit generated files. Any generated artifact may be deleted and recreated from definitions without losing developer-owned behavior.

Generated and handwritten files must be clearly distinguishable.

4. Stable Extension Points Protect Handwritten Code

Custom behavior belongs in partial classes, companion files, or other explicitly developer-owned extension points. Regeneration must not overwrite these files.

An extension point should have a clear lifecycle and a stable contract.

5. Convention Over Structural Choice

PDK uses strong conventions for microservice boundaries, vertical slices, project layout, naming, and generated artifacts. Configuration should express business and infrastructure intent rather than reconstructing the architecture.

Overrides should exist only where real application variation justifies them.

6. One Metadata Model Drives All Outputs

Discovery and validation should produce a unified metadata model. Backend code, contracts, persistence artifacts, documentation, and UI metadata should derive from that model instead of implementing independent interpretations.

7. CLI and Build Generation Are Equivalent

Explicit CLI generation and build-integrated generation must consume the same definitions, validation rules, metadata pipeline, and generators. Invocation method must not change generated results.

8. Diagnostics Before Generation

Invalid definitions should produce stable, actionable diagnostics before files are generated. Expected definition errors should be collected where possible rather than reported as unrelated runtime exceptions.

9. Regeneration Is Deterministic and Idempotent

The same definitions and PDK version should produce the same output. Repeating generation should not modify unchanged files or create duplicate declarations.

Obsolete generated artifacts should be removed safely without touching developer-owned files.

10. Definition Compatibility Has Priority

As PDK evolves, compatibility of existing definitions is the primary stability goal. Generated implementation details may evolve when definitions retain their meaning and regeneration remains safe.

Breaking definition changes require explicit migration guidance and an ADR.

11. Strong Typing Over String Conventions

Public definition APIs should prefer types, generic constraints, and validated value objects over unvalidated strings. Strings remain appropriate for names, display text, and external identifiers when no stronger model is justified.

12. Minimal Definitions, Rich Derived Metadata

Developers should state intent once. PDK should derive conventional names, defaults, and related metadata instead of requiring repetitive declarations. Derived behavior must remain predictable and inspectable.
