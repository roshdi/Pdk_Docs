PDK Architecture

This directory is the source of truth for the architectural intent and decisions of Prime Development Kit (PDK).

Use these documents when designing features, reviewing changes, or deciding between competing implementations. Code should follow accepted decisions. When code and documentation disagree, resolve the conflict explicitly rather than silently changing either one.

Current Reference

  • Vision: product purpose, audience, goals, and boundaries
  • Principles: rules used to guide design tradeoffs
  • Open Questions: unresolved topics requiring decisions
  • Architecture Decision Records: accepted and superseded decisions

Platform projects

The Platform/ folder contains the four platform-level projects:

Project Purpose
*.Core Entity capability interfaces, security abstractions, infrastructure extensions, and shared types. References Pdk.Core.
*.Platform Contains PlatformDefinition, service definitions, and EntityProfiles. References Pdk.Definitions and *.Core.
*.Shared Shared utilities and DTOs available to all projects. References Pdk.Core.
*.Contracts Shared contract types and message definitions. References Pdk.Core.

Service projects

Each built-in and custom service gets its own folder under src/ with five projects following the naming convention {RootNamespace}.{ServiceName}.{ProjectType}:

Project Purpose
*.Core Service-specific core abstractions, entity models, and business logic interfaces.
*.Api Backend API features — commands, queries, handlers, and controllers.
*.Web ASP.NET Core host project with Program.cs for configuring and running the application.
*.UnitTests Unit tests for the service.
*.IntegrationTests Integration tests for the service.

Built-in services (Identity, Notification, File) are selected during scaffolding via the interactive prompt. Custom services (e.g. Customer) are added by the developer for their business domain. All projects target net10.0 with nullable enabled, implicit usings, and the latest C# language version.

PlatformDefinition

The PlatformDefinition.cs file in the Platform project is the single source of truth for the platform configuration. It contains three sections:

Platform

Defines identity metadata for the platform:

Property Description
Name Platform name (e.g. Sales)
RootNamespace Root namespace prefix for all projects (e.g. PdkSample.Sales)
DisplayName Human-readable display name

Infrastructure

Records the technology choices for the platform:

Property Options Description
DatabaseProvider SqlServer, PostgreSql, Oracle, Sqlite Primary database provider
MessageBroker RabbitMq, AzureServiceBus, AmazonSqs, None Message broker selection
CacheProvider Redis, Memory, None Distributed cache provider
OpenTelemetry (flag) Enables OpenTelemetry instrumentation

Infrastructure choices are metadata in the current preview. Selecting PostgreSQL, RabbitMQ, Redis, or OpenTelemetry does not yet produce complete runtime integration for those technologies.

Services

Registers built-in and custom services. The developer can add:

  • Built-in services (IdentityService, NotificationService, FileService) — selected during scaffolding via the interactive prompt. These are currently stubs with no implementation beyond entity profile defaults.
  • Custom services — any additional ServiceDefinition subclass that the developer defines for their business domain.

Services are registered via x.Add<TService>() in the Services(...) section of PlatformDefinition.cs.

Entity Capability Interfaces

The Core project contains an Entities/ folder with default interfaces that add capabilities to entities. Implementing these interfaces on an entity class enables specific behaviors in the generated code.

Interface Capability Properties
ICreatedEntity Creation audit tracking CreatedOn, CreatedBy — auto-set via IRequestContext
IModifiedEntity Modification audit tracking ModifiedOn, ModifiedBy — auto-set when entity changes
IDeletedEntity Soft delete with full audit IsDeleted, DeletedOn, DeletedBy — set/unset methods with timestamp
ISoftDeleteEntity Soft delete (simplified) IsDeleted, DeletedOn, DeletedBy — set/unset without timestamp
IConcurrentEntity Optimistic concurrency Version string for row-level conflict detection

These interfaces are default generated code. Developers can customize them or add any other interfaces as needed.

IConcurrentEntity provides optimistic concurrency via a string Version property that maps to each database provider's native concurrency mechanism (SQL Server rowversion, PostgreSQL xmin, Oracle trigger-incremented NUMBER). Any interface implementing IOptimisticConcurrency is detected automatically by the code generator, which emits HasRowVersion in the entity type configuration. Capability interfaces can also define an optional static Configure method for property-level EF Core configuration (max length, precision, defaults). See the Entity Feature and Capability Guide for details.

The Core project also provides:

  • Security interfaces (IBasicSecurity, IOwnedSecurity, IUnitSecurity) that add permission and scope constraints to entities.
  • IAuthService and IClockService abstractions for authentication and time.
  • RequestContextExtensions that expose Clock and Auth from IRequestContext.

Generation Pipeline

PDK uses a build-integrated generation approach. After pdk new platform scaffolds the platform structure, every subsequent build of the Platform project regenerates all service Core and API projects from the PlatformDefinition source of truth.

Stages

  1. pdk new platform scaffolds the platform solution, Core abstractions, contracts, and the Platform project containing PlatformDefinition.cs.

  2. Build of *.Platform.csproj triggers the AfterBuild MSBuild target, which runs:

    pdk generate platform "$(TargetPath)" "$(ProjectDir)"

  3. pdk generate platform reflects over the compiled PlatformDefinition, initializes the metadata graph, validates all service definitions, and creates or updates all five projects (Core, Api, Web, UnitTests, IntegrationTests) for every registered service.

The first build of the Platform project generates all service projects. Subsequent builds update them when definitions change.

How it works

The AfterBuild target passes the compiled assembly path and project directory to the CLI. GeneratePlatformHandler loads the assembly, discovers the PlatformDefinition subclass, and calls Initialize() — which triggers Configure() on the platform and every registered service. After validation, it iterates over PlatformMetadata.Services and for each service:

  • Creates the service directory at {RootDir}/{ServiceName}/
  • Generates {RootNamespace}.{ServiceName}.Core, {RootNamespace}.{ServiceName}.Api, {RootNamespace}.{ServiceName}.Web, {RootNamespace}.{ServiceName}.UnitTests, and {RootNamespace}.{ServiceName}.IntegrationTests projects
  • Generates entity classes, entity type configurations, feature profiles, and a {ServiceName}DbContext in the Core project
  • Creates or updates the service-specific {ServiceName}.sln
  • Adds all projects to the service solution and the platform solution

Generated files are marked with // <pdk-auto-generated /> and are rewritten only when their content changes; developer-owned files are left intact.

Commands

Command Description
pdk generate platform <assembly> <project-dir> Primary generation command, invoked by the build target
pdk generate api <assembly> <project-dir> Direct invocation with explicit arguments

Key types

  • PlatformDefinition (Pdk.Definitions) — strongly typed source of truth for platform configuration and service registrations. Provides Platform(...), Infrastructure(...), and Services(...) configuration methods.
  • ServiceDefinition (Pdk.Definitions) — abstract base for individual service definitions; exposes Metadata (name, entities, security, dependencies).
  • GeneratePlatformHandler (Pdk.Cli) — loads the compiled platform assembly, initializes the definition, runs diagnostics, and orchestrates code generation via ServiceCoreProjectGenerator and ServiceApiProjectGenerator.
  • GenerateApiHandler (Pdk.Cli) — direct invocation handler with explicit arguments.
  • PlatformConfig (Pdk.Cli) — resolves paths for platform, service, and project locations.
  • GenerationContext (Pdk.Cli) — manages file writes with content-change detection and auto-generated markers.

Updating the Architecture

  1. Update vision.md when product purpose, audience, goals, or boundaries change.
  2. Update principles.md when a durable rule for design tradeoffs changes.
  3. Add unresolved topics to open-questions.md rather than presenting assumptions as decisions.
  4. Add an ADR for a significant decision that constrains future implementation.
  5. Supersede accepted ADRs with a new ADR; do not rewrite their decision history.
  6. Update affected links and current-state documents after a decision is accepted.

Status Vocabulary

  • Proposed: under discussion and not yet authoritative
  • Accepted: approved and authoritative
  • Rejected: considered but intentionally not adopted
  • Superseded: replaced by a newer ADR
