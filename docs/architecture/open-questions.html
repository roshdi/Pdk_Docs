PDK Architecture Open Questions

This file tracks unresolved architectural topics. An answer is not authoritative until it is incorporated into the current architecture and, when significant, recorded in an accepted ADR.

Platform Model

  • How are built-in services different from ordinary service definitions?
  • Can a platform contain multiple instances of one service type with different configuration?
  • Which platform metadata is required, optional, or derived?

Generation Model

  • Which artifacts are always regenerated and which are created once as companion files?
  • How are obsolete generated files identified and removed safely?
  • How should generator versions and metadata schema versions be represented?
  • Should generation run in-process or in an isolated process when invoked by MSBuild?

Compatibility

  • What compatibility guarantees begin with PDK 1.0?
  • How are definition deprecations announced and migrated?
  • Which generated runtime contracts must remain stable across regeneration?

Extensibility

  • Can third parties add definitions, metadata processors, and generators?
  • What is the ordering model for extensions?
  • How are extension conflicts diagnosed?

Runtime Architecture

  • Which runtime capabilities belong in PDK Core versus generated application code?
  • How do services select or override database, messaging, caching, and observability providers? (Partially resolved: each Pdk.Data.* project provides provider-specific extensions such as HasRowVersion converters. Services reference the appropriate provider package.)

Security

  • What is the authoritative model for identity, permissions, scopes, and row-level security?
  • Which security rules are build-time validated and which require runtime evaluation?
