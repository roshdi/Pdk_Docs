Getting Started with PDK

[!IMPORTANT] PDK is an early preview targeting .NET 10. pdk new platform scaffolds a platform, and building its Platform project generates the Core and API project structure for registered services. Generated APIs are intentionally minimal; richer endpoints and frontend generation remain under development.

Prerequisites

  • .NET 10 SDK
  • A terminal with the dotnet command available

Verify the SDK:

dotnet --version

Install the CLI

Install Pdk.Cli as a global .NET tool:

dotnet tool install --global Pdk.Cli

Verify the installation:

pdk --version
pdk --help

To update an existing installation:

dotnet tool update --global Pdk.Cli

Create a Platform

Run the command from the directory that should contain your new platform:

pdk new platform Sales PdkSample.Sales

The name and root namespace are optional initial values. The command remains interactive and asks for:

  1. Platform name
  2. Root namespace
  3. Database provider: SQL Server, PostgreSQL, Oracle, or SQLite
  4. Optional Identity, Notification, and File service definitions
  5. Zero or more business-service names

Use Space to toggle built-in services and Enter to continue. Submit an empty business-service name to finish.

The command will not overwrite an existing platform directory.

Platform projects

The Platform/ folder contains the four platform-level projects:

Project Purpose
*.Core Entity capability interfaces, security abstractions, infrastructure extensions, and shared types. References Pdk.Core.
*.Platform Contains PlatformDefinition, service definitions, and EntityProfiles. References Pdk.Definitions and *.Core.
*.Shared Shared utilities and DTOs available to all projects. References Pdk.Core.
*.Contracts Shared contract types and message definitions. References Pdk.Core.

Service projects

Each service gets its own folder under src/ with five projects following the naming convention {RootNamespace}.{ServiceName}.{ProjectType}:

Project Purpose
*.Core Service-specific core abstractions, entity models, and business logic interfaces.
*.Api Backend API features — commands, queries, handlers, and controllers.
*.Web ASP.NET Core host with Program.cs for configuring and running the application.
*.UnitTests Unit tests for the service.
*.IntegrationTests Integration tests for the service.

Built-in services (Identity, Notification, File) are selected during scaffolding via the interactive prompt. Custom services (e.g. Customer) are added by the developer for their business domain. All projects target net10.0.

Inspect the Platform Definition

Open PlatformDefinition.cs. It contains three configuration sections:

Platform

Defines the identity metadata for the platform:

Platform(platform =>
{
    platform.Name("Sales")
            .RootNamespace("PdkSample.Sales")
            .DisplayName("Sales Platform");
});
Property Description
Name Platform name, used for directory and solution naming
RootNamespace Root namespace prefix for all generated projects
DisplayName Human-readable display name

Infrastructure

Records the technology choices for the platform:

Infrastructure(infra =>
{
    infra.DefaultDatabase(DatabaseProvider.PostgreSql)
         .MessageBroker(MessageBroker.RabbitMq)
         .Cache(CacheProvider.Redis)
         .OpenTelemetry();
});
Property Options Description
DatabaseProvider SqlServer, PostgreSql, Oracle, Sqlite Primary database provider
MessageBroker RabbitMq, AzureServiceBus, AmazonSqs, None Message broker selection
CacheProvider Redis, Memory, None Distributed cache provider
OpenTelemetry (flag) Enables OpenTelemetry instrumentation

Infrastructure choices are metadata in the current preview. Selecting PostgreSQL, RabbitMQ, Redis, or OpenTelemetry does not yet generate complete runtime integration for those technologies.

Services

Registers built-in and custom services:

Services(services =>
{
    services.Add<IdentityService>();
    services.Add<NotificationService>();
    services.Add<FileService>();
    // services.Add<OrderService>();
});

The developer can add:

  • Built-in services — IdentityService, NotificationService, FileService. These are currently stubs with no implementation beyond entity profile defaults. They are selected during scaffolding via the interactive prompt.
  • Custom services — any additional ServiceDefinition subclass that the developer defines for their business domain. Each custom service gets its own {ServiceName}Service.cs file and {ServiceName}.sln solution.

Use x.Add<TService>() in the Services(...) section to register a service.

Define an Entity

A generated business-service definition can describe entities:

protected override void Configure()
{
    Entities(entities =>
    {
        entities.DefaultProfile(EntityProfiles.ConcurrentHistory);

        entities.Entity("Customer")
            .Table("Customers");
    });
}

The definition model also supports profiles, interfaces, service dependencies, security capabilities, and permissions. These APIs produce metadata for evolving generators; they do not yet produce a complete runnable service.

See the Entity Feature and Capability Guide.

Entity Capability Interfaces

The Core project contains an Entities/ folder with default interfaces that add capabilities to entities. Implementing these interfaces on an entity class enables specific behaviors:

Interface Capability Properties
ICreatedEntity Creation audit tracking CreatedOn, CreatedBy — auto-set via IRequestContext
IModifiedEntity Modification audit tracking ModifiedOn, ModifiedBy — auto-set when entity changes
IDeletedEntity Soft delete with full audit IsDeleted, DeletedOn, DeletedBy — set/unset methods with timestamp
ISoftDeleteEntity Soft delete (simplified) IsDeleted, DeletedOn, DeletedBy — set/unset without timestamp
IConcurrentEntity Optimistic concurrency Version string for row-level conflict detection

These are default generated code and serve as a starting point. Developers can customize them or add any other interfaces as needed. IConcurrentEntity is the default concurrency interface; any interface implementing IOptimisticConcurrency is detected automatically and mapped to the database's native concurrency mechanism via provider-specific converters in Pdk.Data.* packages.

The Core project also provides:

  • Security interfaces (IBasicSecurity, IOwnedSecurity, IUnitSecurity) that add permission and scope constraints to entities.
  • IAuthService and IClockService abstractions for authentication and time.
  • RequestContextExtensions that expose Clock and Auth from IRequestContext.

Build the Solution

cd Sales/src
dotnet restore
dotnet build Sales.sln

Building the solution also builds the Platform project. Its AfterBuild target runs pdk generate platform, which reflects over the compiled PlatformDefinition and creates or updates all five projects (Core, Api, Web, UnitTests, IntegrationTests) for every registered service. The first build generates all service projects; subsequent builds update them when definitions change.

Keep the global pdk tool available when building generated projects. Rebuild just the Platform project when you change definitions:

dotnet build Platform/PdkSample.Sales.Platform/PdkSample.Sales.Platform.csproj

The same operation can be invoked directly for troubleshooting or CI:

pdk generate platform <path-to-platform.dll> <path-to-platform-project-directory>

Current Preview Limitations

  • Service Core and API projects are scaffolded from registered service definitions; their generated API host currently provides only the baseline health endpoint.
  • Database selection currently records metadata only.
  • Entity, persistence, migration, endpoint, and deployment generation are incomplete.
  • Metadata export is experimental and does not yet write the final export artifact.
  • Angular and PrimeNG UI generation are planned but not implemented.
  • Commands such as pdk add service and pdk entity are incomplete.

Use the CLI Guide for command details and the architecture reference for PDK's intended direction.
