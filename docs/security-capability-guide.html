Security Capabilities

Overview

PDK provides a metadata-driven security model for implementing both permission-based authorization and row-level security.

Instead of writing authorization logic inside every query, command, or repository, security is declared as reusable capabilities using C# interfaces.

A security capability defines:

  • Default permissions generated for the entity.
  • Available permission scopes.
  • Optional row-level security filters.
  • Metadata that can be consumed by generators and administration UI.

This allows the same security capability to be shared by many entities while keeping the implementation centralized.

Security Model

PDK separates authorization into two independent concepts.

Permission

A permission determines what operation a user is allowed to perform.

Examples:

  • Customer.Read
  • Customer.Create
  • Customer.Update
  • Customer.Delete

Permissions are generated automatically from the implemented security capability.

Scope

A scope determines which records are accessible.

Examples:

Permission Scope
Customer.Read All
Customer.Read Owner
Customer.Read Unit
Customer.Read Warehouse

A permission without a valid scope does not grant access to any records.

Security Grant

For scoped permissions, PDK stores additional constraint values inside a SecurityGrant.

Examples:

Unit Security

{
    "values":[1,3,5]
}

User can access only units:

  • 1
  • 3
  • 5

Warehouse Security

[
    {
        "values1":[1],
        "values2":[1,2]
    },
    {
        "values1":[2],
        "values2":[2,3]
    }
]

Meaning:

  • Warehouse 1 → Document Types 1 and 2
  • Warehouse 2 → Document Types 2 and 3

Each object represents one logical rule.

Multiple rules are combined using OR.

Values inside one rule are combined using AND.

Equivalent SQL:

(
    WarehouseId = 1
    AND
    DocumentType IN (1,2)
)
OR
(
    WarehouseId = 2
    AND
    DocumentType IN (2,3)
)

Creating a Security Capability

Every security capability implements ISecurity.

A capability can be shared by many entities across the platform.

Basic Security

Basic security only controls permissions and does not apply row-level filtering.

public interface IBasicSecurity : ISecurity
{
    static string[] ISecurity.GetDefaultPermissions()
    {
        return ["Read", "Create", "Update", "Delete"];
    }

    static SecurityScopeDefinition[] ISecurity.GetAvailableScopes()
    {
        return
        [
            SecurityScopes.None,
            SecurityScopes.All
        ];
    }
}

This capability provides two scopes:

  • None
  • All

No row filter is required.

Owner Security

Owner security restricts records to the current authenticated user.

Entities implementing this capability must expose an OwnerId property.

public interface IOwnedSecurity : ISecurity, ICreated
{
    AuthId OwnerId { get; set; }

    static string[] ISecurity.GetDefaultPermissions()
    {
        return ["Read", "Create", "Update", "Delete"];
    }

    static SecurityScopeDefinition[] ISecurity.GetAvailableScopes()
    {
        return
        [
            SecurityScopes.None,
            SecurityScopes.Owner,
            SecurityScopes.All
        ];
    }

    void ICreated.SetCreated(IRequestContext context)
    {
        OwnerId = context.Auth.CurrentUserId;
    }

    [SecurityFilter]
    static Expression<Func<T,bool>> OwnerFilter<T>(
        IRequestContext context)
        where T : IOwnedSecurity
    {
        var currentUserId = context.Auth.CurrentUserId;

        return e => e.OwnerId == currentUserId;
    }
}

Generated SQL:

WHERE OwnerId = CurrentUserId

Unit Security

Unit security restricts data using one security dimension.

public interface IUnitSecurity : ISecurity
{
    long UnitId { get; set; }

    static string[] ISecurity.GetDefaultPermissions()
    {
        return ["Read", "Create", "Update", "Delete"];
    }

    static SecurityScopeDefinition[] ISecurity.GetAvailableScopes()
    {
        return
        [
            SecurityScopes.None,
            SecurityScopes.Unit,
            SecurityScopes.All
        ];
    }

    [SecurityFilter]
    static Expression<Func<T,bool>> UnitFilter<T>(
        IRequestContext context,
        SecurityGrant securityGrant)
        where T : IUnitSecurity
    {
        return securityGrant
            .GetSecurityConstraints<long>()
            .CreateFilter()
            .WithParameter<T>(e => e.UnitId);
    }
}

Generated SQL:

WHERE UnitId IN (...)

Applying a Security Capability

Simply implement the desired interface.

public class WarehouseDocument :
    Entity,
    IWarehouseSecurity
{
    public long WarehouseId { get; set; }

    public int DocumentType { get; set; }

    ...
}

No additional configuration is required.

SecurityFilter Attribute

Methods decorated with SecurityFilterAttribute are discovered automatically by PDK.

The generated filter is applied to every secured query.

[SecurityFilter]
static Expression<Func<T,bool>> Filter<T>(...)

The method must:

  • Be static
  • Return Expression<Func<T,bool>>
  • Be generic
  • Constrain T to the implemented security capability

Example:

where T : IUnitSecurity

SecurityConstraint Helpers

PDK provides helper classes for building EF Core compatible expressions.

Single dimension:

securityGrant
    .GetSecurityConstraints<long>()
    .CreateFilter()
    .WithParameter<T>(e => e.UnitId);

Two dimensions:

securityGrant
    .GetSecurityConstraints<long,int>()
    .CreateFilter()
    .WithParameters<T>(
        e => e.WarehouseId,
        e => e.DocumentType);

Three dimensions:

securityGrant
    .GetSecurityConstraints<long,int,Guid>()
    .CreateFilter()
    .WithParameters<T>(
        e => e.CompanyId,
        e => e.WarehouseId,
        e => e.DocumentType);

These builders generate expression trees that are fully translatable by Entity Framework Core.

Creating Custom Security Capabilities

Developers can create custom capabilities for any business requirement.

Example:

public interface IProjectSecurity : ISecurity
{
    Guid ProjectId { get; set; }

    static string[] ISecurity.GetDefaultPermissions()
    {
        return ["Read", "Create", "Update", "Delete"];
    }

    static SecurityScopeDefinition[] ISecurity.GetAvailableScopes()
    {
        return
        [
            SecurityScopes.None,
            SecurityScopes.Project,
            SecurityScopes.All
        ];
    }

    [SecurityFilter]
    static Expression<Func<T,bool>> ProjectFilter<T>(
        IRequestContext context,
        SecurityGrant securityGrant)
        where T : IProjectSecurity
    {
        return securityGrant
            .GetSecurityConstraints<Guid>()
            .CreateFilter()
            .WithParameter<T>(e => e.ProjectId);
    }
}

Best Practices

  • Keep security capabilities small and reusable.
  • Share capabilities across entities whenever possible.
  • Prefer reusable security interfaces over writing filters inside queries.
  • Use SecurityConstraint builders instead of manually building expression trees.
  • Keep security logic inside the capability interface, not inside repositories.
  • Model each independent security dimension as a separate property.
  • Use multi-dimensional constraints only when security values are correlated.

Benefits

Using security capabilities provides:

  • Centralized authorization logic
  • Reusable row-level security
  • Automatic permission generation
  • EF Core compatible filters
  • Strongly typed security expressions
  • Metadata suitable for code generation
  • Consistent security implementation across all microservices
  • Simplified maintenance and testing
